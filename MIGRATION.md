# Migration plan: self-hosted full-stack TTP (not started)

**Status:** planned only — nothing here is implemented. The live app stays the v1 PWA on
GitHub Pages (`SPEC.md`) until we decide to start this.

**Goal:** turn TTP into a full-stack app with a backend and Postgres, hosted on the owner's
old laptop (Linux Mint), reachable from the internet so friends can use it with their own
accounts.

---

## 1. Why this is a big change

Today TTP has **no server**: every byte of data lives in SQLite (WASM, OPFS) on the phone,
and GitHub Pages only serves static files. Moving to a laptop with Postgres means three new
pieces, because a browser cannot talk to Postgres directly:

1. **Postgres** on the laptop.
2. **An API** between the app and Postgres (a small Node server, or an off-the-shelf tool).
3. **A way to reach the laptop** over HTTPS from anywhere (gym, friends' phones).

Adding friends adds two more:

4. **Accounts** — sign-up/login, password hashing, every row owned by a user, every query
   filtered by the logged-in user.
5. **Security work** — friends' data sits on a machine in your home: hashed passwords, login
   rate limiting, firewall, Postgres never exposed, backups, OS updates.

What carries over: all screens and the design, `src/domain/` (pure logic + tests), the
Hevy-style workout flow. What gets rewritten: the storage layer (`src/db/`, the SQL in
`src/repositories/` moves to the server; repositories become API calls).

## 2. Options we discussed

### 2.1 Where the data lives during a workout
| Option | How it works | Pros | Cons |
|---|---|---|---|
| **A. Local-first + sync** | Phone keeps SQLite as today and syncs to Postgres when online | Works in airplane mode; instant | Most work (sync, conflicts) |
| **B. Server-first** | Phone reads/writes the API live | Simplest data model | No signal = can't log a set; laptop must be up |
| **C. Hybrid (chosen)** | Server is the source of truth; only the **in-progress workout** is a local document that syncs when the connection returns | Gym-proof where it matters, simple elsewhere | Small sync layer for one document |

Tools for local-first sync if we ever want option A: **PowerSync** (free self-hosted
edition), **ElectricSQL** — both sync Postgres ↔ SQLite on the device.

### 2.2 API layer
- **Own small Node + TypeScript server (chosen)** — same language as the app, full control
  over auth and per-user filtering. Framework: Hono (tiny, typed).
- **PostgREST** — instant REST API over a Postgres schema, no backend code; auth via JWT +
  row-level security.
- **Supabase self-hosted** — Postgres + REST + auth + storage in one package; heavier
  (many containers) for an old laptop.

### 2.3 Reaching the laptop from the internet
| Option | Notes |
|---|---|
| **Tailscale Funnel (chosen)** | Free, no domain to buy, no router changes, home IP hidden. Public HTTPS URL like `https://ttp-laptop.<tailnet>.ts.net`. `tailscale funnel --bg 3000`. |
| Cloudflare Tunnel + own domain | Nicer URL (`ttp.yourname.com`), Cloudflare DDoS protection; needs a domain (~$10/yr) in Cloudflare. |
| Tailscale (private, no Funnel) | Only devices in your tailnet can reach it — great for just you, awkward for friends. |
| Router port forwarding + Let's Encrypt | Exposes your home IP, depends on your ISP. Avoid. |

### 2.4 Running it on the laptop
- **Docker Compose (chosen)**: `app` (Node) + `db` (Postgres) containers, Postgres on the
  internal network only.
- Optional web dashboards instead of the command line: **Coolify**, **Dokploy**, **CasaOS**.

## 4. Target architecture
```
Phone / friends' browsers ──HTTPS──▶ Tailscale Funnel ──▶ laptop :3000
                                                          └─ docker compose
                                                             ├─ app: Node 24 + TS (Hono)
                                                             │    • serves the built React app
                                                             │    • JSON API under /api
                                                             └─ db: Postgres (internal only,
                                                                  nightly pg_dump backups)
```
- App and API on the **same origin** → cookie sessions, no CORS.
- Only the app port is exposed (through Funnel). Postgres is never published.

Proposed layout:
```
server/
  index.ts       # Hono: static files + /api routes
  db.ts          # postgres.js client + migrations runner (schema_migrations table)
  migrations/    # 001_init.sql, … — never edit an applied one
  auth.ts        # sessions, argon2id, invite codes, login rate limit
  routes/        # exercises, workouts, plan, skips, progress, settings, import
  cli.ts         # `invite` (create code), `users` (list)
src/             # React app as today; repositories call the API via api/client.ts
```
New dependencies (to approve when we start): `hono`, `@hono/node-server`, `postgres`,
`@node-rs/argon2`, `zod`; dev: `tsx`.

## 5. Data model (Postgres)
Same tables as v1 plus ownership; **every user-owned query filters by the session's user id**.
- `app_user(id, username UNIQUE case-insensitive, password_hash, created_at)`
- `session(token_hash PK, user_id, created_at, expires_at)` — 30-day sliding expiry
- `invite(code PK, created_at, used_by, used_at)`
- `user_settings(user_id PK, default_rest_seconds)`
- `exercise(id, user_id, name, muscle_group, equipment, is_custom, archived, rest_seconds,
  rest_custom, favorite, image, has_grip)` — the 52-exercise seed library is **copied into
  each new account**, so favourites / rest / grip / photo / archive stay per user with no
  extra tables. `UNIQUE (user_id, lower(name))`.
- `workout(id UUID, user_id, title, date, started_at, finished_at, notes, rest_ends_at)` —
  one unfinished workout per user (partial unique index)
- `workout_exercise(id UUID, workout_id, exercise_id, position, grip)`
- `workout_set(id UUID, workout_exercise_id, position, set_type, weight_kg, reps, completed)`
- `plan_version(id, user_id, effective_from)`, `plan_day(plan_version_id, weekday)`
- `skip(user_id, date, reason, note)`, PK `(user_id, date)`

Workout / exercise / set ids are **client-generated UUIDs**, so the phone can create them
while offline.

## 6. Auth & security
- Sign-up: username + password (≥ 10 chars) + one-time invite code.
  Owner creates codes: `docker compose exec app node dist-server/cli.js invite`.
- Passwords hashed with **argon2id**.
- Session: random 32-byte token in an `HttpOnly; Secure; SameSite=Lax` cookie; only its
  SHA-256 is stored in the DB.
- Login rate limit: 10 attempts / 15 min per IP + username.
- State-changing requests must be `application/json` (blocks form-based CSRF).
- Security headers (CSP, `nosniff`, `frame-ancestors 'none'`); request body limit ~2 MB
  (exercise photos).
- Postgres only on the internal Docker network; app container runs as non-root.
- Laptop: automatic security updates, firewall (`ufw`) with nothing inbound except via
  Tailscale.

## 7. "Online, but the workout survives drops"
- Everything except the active workout goes through the API; failed requests show a clear
  "You're offline" state.
- The **active workout is a local-first document**: the editor works on a copy in memory +
  `localStorage`, every change applies instantly, and the whole document is synced with
  `PUT /api/workouts/:id` (debounced ~1 s, retried with backoff while offline, flushed when
  the app goes to the background). Last write wins — fine for one person on one phone.
- "Previous" values are fetched when an exercise is added and stored in the document, so
  they keep working offline.
- Banner while unsynced changes exist: "Offline — changes will sync".

## 8. Things to watch
- **The app's address is tied to its data.** v1 data lives in the phone's storage for
  `crusaderrrr.github.io`. A new URL (the `.ts.net` one) starts empty. Use **Settings →
  Export** in v1 first, then import into your new account (phase 11).
- **HTTPS is mandatory** (PWA, cookies). Funnel provides it.
- **An old laptop is a single point of failure**: disable suspend on lid close, keep it on
  power, nightly `pg_dump` (keep 14), copy backups off the laptop now and then.
- **Funnel limits**: Tailscale Funnel has bandwidth limits — fine for a few friends, not for
  a public app.
- **Scope**: `CLAUDE.md` lists accounts and sync as out of scope for v1; this plan is v2.

## 9. Phases (when we start)
7. **Server skeleton** — Hono + Postgres + migrations + serves the SPA; Docker Compose; CI
   runs server tests against a Postgres service.
8. **Accounts** — invites, sign-up, login, logout, sessions, rate limit; login/sign-up
   screens.
9. **API + client** for exercises, plan, skips, history, progress, settings (repositories
   become API calls).
10. **Local-first active workout** document + background sync + offline banner.
11. **Import a v1 backup** into an account (browser reads the `.sqlite3` with sqlite-wasm,
    posts JSON to `POST /api/import`).
12. **Deploy on the laptop** — `DEPLOY.md` (Docker Engine on Mint, `.env`, `docker compose
    up -d`, Tailscale + Funnel, backups timer, updates); old GitHub Pages site becomes a
    "moved to …" page.

Work happens on a `fullstack` branch so the live v1 keeps working until the switch.
